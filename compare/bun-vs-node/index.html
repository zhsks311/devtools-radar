Bun vs Node.js

Bun's own test count says node:http passes 403 of 415 tests, and Node's own calendar says v20 died on 24 March 2026. Neither runtime charges a cent, so the bill arrives somewhere else.

Verdict

Pick Node if your service needs an API Bun documents as missing — getPeerCertificate(), SNICallback, createHook with real async ids — or if a native addon in your tree has no build for NODE_MODULE_VERSION 147. Pick Bun if the addons and APIs you depend on survive its 403-of-415 node:http count, because the runtime itself will never appear on an invoice.

1. Both runtimes cost nothing, so the invoice arrives as labour

Bun is MIT. Node.js is MIT. Neither sells a paid tier, so the bill is engineer-hours on three meters: the release calendar, the compatibility surface and the native-module ABI.

For teams maintaining a Node service: as of 10 November 2026, both runtimes have no price.

  • Node: Node publishes a release calendar; v26 Lithium, v24 Krypton and v22 Jod are LTS.
  • Bun: 1.4.0 (20 August 2026) combined the Rust rewrite with the compatibility-target move from 24.3.0 to 26.3.0 and native ABI 147.

For Bun 1.4, check whether your native addons have builds for NODE_MODULE_VERSION 147.

Node's release page reads like a work schedule:

Support window and release cycle:

  1. LTS "typically guarantees that critical bugs will be fixed for a total of 30 months" (Node's wording).
  2. Starting with v27, the cycle becomes annual: every major gets six months of Alpha, six of Current, then LTS.

Read it as a penalty table. It punishes the team that adopts a major and forgets it: v20 lived from 17 Apr 2023 to 24 Mar 2026, about 35 months.

If production still runs Node 20, plan a move to Node 24 or 26 LTS: Node 20 reached EOL on 24 March 2026.

3. Who should not pick Node for unbuilt TypeScript

Type stripping is on by default, stable since v25.2.0 / v24.12.0. Node executes erasable syntax without type checking; other syntax needs separate tooling.

// runs on Node 26 with no flags: every annotation here is erasable
type Host = string;
const host: Host = process.env.HOST ?? "localhost";
console.log(`binding ${host}`);

enum throws ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX.

Node 26 also refuses:

  • namespace with runtime code, parameter properties, import aliases: same error
  • .tsx files
  • paths, because tsconfig.json is ignored
  • TypeScript inside node_modules
  • parsing without WebAssembly: ERR_WEBASSEMBLY_NOT_SUPPORTED

This meter punishes codebases built on enums and path aliases; for them, the build step stays.

Bun says it plainly: "Bun is not 100% compatible with Node.js yet." Bun's own 1.4 counts against the Node 26.3.0 suite:

The ABI tax: 1.4 moved the compatibility target from 24.3.0 to 26.3.0. NODE_MODULE_VERSION is now 147, so native addons built for Node 24 must be rebuilt.

Check required inspector APIs; module pass counts are not application coverage.

5. Who should not pick Bun: teams requiring missing APIs

Bun's compatibility docs name the gaps. Map each to a service you run:

  • HTTP servers tuned for a load balancer. http.Server does not extend net.Server, the keepAlive / keepAliveInitialDelay server options are no-ops, and listen(handle) is ignored. Your keep-alive tuning silently does nothing.
  • mTLS and multi-tenant TLS. node:https lacks getPeerCertificate() and getCipher() and does not support SNICallback. Retain Node if you require these APIs.
  • Signing code. BoringSSL-backed node:crypto lacks ed448, x448, rsa-pss and dsa keys, has no secp256k1 curve and no chacha20-poly1305.
  • APM tracing. async_hooks createHook is a stub and async ids are always 0; correlation by async id collapses.
  • cluster fleets on macOS or Windows. HTTP load-balancing across workers only works on Linux, via SO_REUSEPORT.

AsyncLocalStorage context does not propagate into Worker/BroadcastChannel events in Bun.

6. Bun stays MIT after Anthropic's acquisition; check before migrating

Anthropic acquired Bun on 2 December 2025. Claude Code ships as a Bun executable (Bun's statement), and Bun's founder wrote then: "Today, Bun makes $0 in revenue." Bun stays MIT.

The acquisition changes who pays for Bun's roadmap. It does not change the licence, and it does not change the API surface you have to test.

Check today:

  1. List every .node addon in the tree and whether it has a build for NODE_MODULE_VERSION 147.
  2. Check required HTTP APIs, createHook, distinct async IDs, getPeerCertificate and SNICallback against Bun's gaps.
  3. Write down the EOL date of the Node major running in production.

What you gain, what you give up

Bun

You gain
  • JavaScript, TypeScript, JSX and bundling from one executable, so no separate tsc, test runner or bundler
  • 1,517 more Node test-suite tests pass in 1.4, and node:sqlite passes 18 of 18 by Bun's own count
  • Bun's own hello.js benchmark: 5.1 ms vs 27.2 ms start-up on Linux, 14.6 MB vs 44.5 MB peak memory
  • MIT licensed after the Anthropic acquisition, with the Node compatibility target moved to 26.3.0
You give up
  • node:http passes 403 of 415 of Node's own tests, and http.Server does not extend net.Server
  • node:https lacks getPeerCertificate() and getCipher(), and SNICallback is unsupported
  • NODE_MODULE_VERSION 147 means addons built for Node 24 must be rebuilt
  • Bun's own memory table shows the Vite dev server at 233 MB vs 214 MB on Node

Node.js

You gain
  • A dated calendar: v26 Lithium and v24 Krypton are LTS, and LTS typically guarantees fixes for 30 months
  • Native addons are the default path, and ABI builds target the runtime you actually run
  • TypeScript type stripping runs with no build step for erasable syntax
  • Nothing to license, and commercial support exists through OpenJS partners after LTS ends
You give up
  • Type stripping refuses enum, .tsx, parameter properties, import aliases and tsconfig paths
  • TypeScript inside node_modules is refused outright
  • Parsing requires WebAssembly, or the parser throws ERR_WEBASSEMBLY_NOT_SUPPORTED
  • v20 and v25 both reached end of life in 2026, so the calendar forces migrations

Migration path

What switching actually takes

Moving to Bun starts with bun install reading the same package.json, but every native addon needs a build for NODE_MODULE_VERSION 147 before it loads, so the hook stampede is the first thing to schedule. Moving back is not automatic either: Bun's compatibility docs list the API gaps you will meet — getPeerCertificate(), SNICallback, async_hooks — and there is no tool that rewrites handlers around them. Run the service test suite under both runtimes before either direction, then keep the loser's addon builds around for a release or two.

Questions that change the decision

Does Node 26 type-check TypeScript?
No: type stripping performs no type checking, so a separate tool is still required. Decorators are a parser error, and --experimental-transform-types was removed in v26.0.0.
Is Bun faster than Node?
Bun's own hello.js benchmark puts Linux start-up at 5.1 ms for Bun 1.4 versus 27.2 ms for Node.js 26; these are vendor measurements, not independent ones. Separately, Bun's peak-memory figures under load, with 1,000,000 requests and 64 connections, put the Vite dev server at 233 MB on Bun versus 214 MB on Node, so Bun is not lighter everywhere.
Can I buy support for a Node major after LTS ends?
Not from the Node.js project itself. Commercial support past Maintenance LTS is sold by OpenJS Ecosystem Sustainability Program partners.
Does Bun's MIT licence cover everything in the binary?
No: Bun statically links JavaScriptCore/WebKit, which is LGPL-2. That is why Bun's licence file spells out relinking obligations.
