Supabase vs Firebase

Fifty users watching a hundred documents that change twenty times a minute cost about $1,296 a month in Firestore reads, and a flat $25 on one Supabase Pro Micro project. The screen is identical; the only thing that changed is what the vendor counts.

Verdict

If your bill grows with how often people watch data rather than how much data you keep, Supabase wins: that dashboard is about $1,296/month of Firestore reads against $25 for one Pro Micro project. If your app fits Firestore's daily free quota of 50,000 reads, 20,000 writes and 20,000 deletes, stay where you are, because leaving costs a schema project and a password path the migration repo still marks incomplete.

1. The billing unit decides what code you may write

Supabase sells a machine. You rent a Postgres instance, a disk and a connection ceiling, and reads inside them are free. Firebase sells events. Every document read, write, index batch and listener update is a line on the invoice, with a daily free quota on top.

What each philosophy forbids:

  • Firestore forbids JOINs. A relation becomes duplicated fields or an extra round trip, and the extra reads are billed.
  • Supabase forbids cheap concurrency. The $10 Micro instance stops at 60 direct and 200 pooled connections. The ceiling is purchasable rather than absolute — 12,000 pooled connections at $3,730 — but you buy it per project.

2. A listener is a meter, not a subscription

A listener is not a free subscription. Firestore bills a read each time a document enters or updates in a live listener's result set, and one more when a change pushes it out. The meter runs while nobody clicks. Don't pick Firestore for a screen that stays open all day.

Take 50 users, each watching 100 documents that change 20 times a minute:

users, docs, changes_per_min = 50, 100, 20
reads = users * docs * changes_per_min * 60 * 24 * 30
print(reads)                   # 4.32B events, zero clicks
print(reads / 100_000 * 0.03)  # 43,200 x $0.03, before free quota

That is a gross read charge at the us-central1 rate, before free-quota adjustments. One Pro Micro project costs $25/month inside its quotas — which says nothing about whether that instance can carry the load, only that the bill stops tracking the watching. Reconnects make it worse:

  • Offline persistence off: every reconnect is billed like a brand-new query.
  • Persistence on but disconnected for more than 30 minutes: same bill.

3. On Supabase the ceiling is capacity, not a per-read meter

Postgres Changes is a database event stream, and you opt in per table:

Add a table to the publication: alter publication supabase_realtime add table your_table_name;

Nothing in that stream is metered per read. What runs out is the instance: its compute tier and its connection and pooler limits. Compute is billed per project, separately from the plan.

4. Index entry reads are the Firestore line item nobody quotes

  • One read per batch of up to 1,000 index entries a query reads.
  • A query with one range field pays nothing for index entries. Zero range fields are also exempt. Add a second range field and billing starts.
  • count(), sum() and avg() bill index reads, with a 1-document-read minimum even at zero entries.

Firestore's own docs give the example: count() over 1,500 index entries bills 2 document reads.

Ten million plain reads cost $3.00 at the listed rate. The count() in your page header is a different bill.

Audit any query that combines two range fields before it ships.

5. Migration is a schema project with a script attached

supabase-community/firebase-to-supabase on GitHub is community tooling, not an official CLI. What it does:

  1. firestore2json.js exports a collection; json2supabase.js loads it into a table. One collection, one table.
  2. Fields are flattened to text, numeric, boolean or jsonb.
  3. Splitting nested JSON into related tables needs custom hooks you write.

Auth is the sharper edge. firestoreusers2json and import_users move users, importing hashes with Firestore's SCRYPT parameters (base64_signer_key, base64_salt_separator, rounds, mem_cost).

Verifying an existing Firebase password on first login needs a middleware the repo itself marks work in progress. The AWS Lambda variant is listed as TBD.

Until that middleware exists, plan for blocked logins at cutover and decide in advance whether you force a password reset.

6. Pick by bill shape first, then by blockers

Choose Supabase when modeled Firestore charges exceed the plan and compute cost and the workload fits the selected tier and quotas. Keep Firestore when all free allowances fit:

  • 50,000 reads, 20,000 writes and 20,000 deletes per day.
  • 1 GiB stored, 10 GiB/month outbound; one free database per project.

Check today, in this order:

  1. Multiply listeners × documents per listener × changes per minute × (60 × 24 × 30) minutes, then × $0.03 per 100,000.
  2. Find every hot-path query with two range fields or a count().
  3. On Supabase, compare peak database connections to Micro's 60 direct / 200 pooled.
  4. Check whether first-login existing-password verification blocks migration.

What you gain, what you give up

Supabase

You gain
  • One invoice for compute, disk and connections — reads inside the instance are not metered
  • pgvector lives in the same Postgres as your rows, so RAG needs no second system
  • Standard Postgres: SQL, JOINs, transactions, triggers, and pg_dump as an exit door
  • The connection ceiling is purchasable: 200 pooled connections on $10 Micro up to 12,000 on $3,730
You give up
  • You buy headroom, not usage: peak connections decide the tier, and idle capacity still bills
  • Every extra project adds its own compute line ($10 for a Micro) even on one Pro plan
  • Free projects are paused after a week of inactivity, which kills demo and staging projects
  • Realtime subscriber capacity is not on the price sheet; you size by connection and compute limits

Firebase

You gain
  • Offline persistence and multi-platform SDKs that work when the network does not
  • No connection pool to size: events are metered, not sockets
  • A daily free quota of 50,000 reads and 20,000 writes per project
  • Listeners bill only for documents that change in the result set, not for every poll
You give up
  • A dashboard left open all day is a recurring read charge: 50 users can pass $1,296/month
  • Reconnects are billed like brand-new queries — with persistence off, every one of them
  • Index entry reads are a second meter: a second range field starts billing
  • No JOIN, and the export tool flattens one collection to one table, so schema design lands on you

Migration path

What switching actually takes

supabase-community/firebase-to-supabase is community tooling, not an official CLI. firestore2json.js exports one collection, json2supabase.js loads it into one table, and fields are flattened to text, numeric, boolean or jsonb — splitting nested JSON into related tables is a hook you write. Auth is the harder half: firestoreusers2json and import_users carry passwords over as SCRYPT hash parameters, and verifying a user's existing Firebase password on first login needs middleware the repo still marks work in progress. Budget the schema work, not the script.

Common questions

Can I park a Supabase Free project for a demo that sits idle?
Not reliably: Free projects are paused after 1 week of inactivity, and Free allows only 2 active projects. Pro projects are never paused for inactivity.
Does offset pagination save reads on Firestore?
No. Firestore bills a read for every skipped document, so offset 10 returning 1 document costs 11 reads.
Will Supabase Realtime leak rows a user shouldn't see?
Postgres Changes subscriptions are RLS-aware, so clients receive only rows they are allowed to select. Supabase's docs also document Broadcast as an alternative way to subscribe to database changes.
How is Firestore vector search billed?
kNN vector search bills one read per batch of up to 100 vector index entries. That is a tenth of the 1,000-entry batch size used for regular index entry reads.
